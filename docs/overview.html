이 봇이 해주는 일 — 리뷰어가 보는 화면

Slack에서 무엇을 받고, 버튼을 누르면 무슨 일이 일어나는지를 순서대로 보여줍니다. 코드를 몰라도 읽을 수 있게 썼습니다. 구조가 궁금해지면 문서 안내로 돌아가 architecture로 넘어가세요.

v1 최종 갱신 2026-09-28 독자 전원 성격 소개 · 요약
01

무엇을 해결하나

문제 ① 리뷰가 밀린다
MR은 열려 있는데 아무도 안 본다
  • MR이 열린 사실을 아무도 모른 채 하루가 지나갑니다.
  • 알게 되더라도 뭐가 바뀌었는지 파악하는 비용이 커서 뒤로 미뤄집니다.
  • 승인하려면 GitLab을 열고, 찾아 들어가고, 다시 읽어야 합니다.
문제 ② 의견이 왕복한다
"이 값 좀 고쳐주세요" 한 줄의 왕복
  • 코멘트를 남기면 작성자가 볼 때까지 멈춥니다.
  • 사소한 수정 하나에 반나절이 사라집니다.
이 봇의 답
Slack 한 통 안에서 끝낸다
  • MR이 열리면 요약과 함께 Slack으로 먼저 찾아옵니다.
  • 버튼 하나로 승인하거나, 의견을 적어 넣으면 LLM이 실제로 고쳐 push하고 결과를 다시 알립니다.
  • 문서 MR은 무엇이 어떻게 바뀌었는지를 검증된 리포트로 정리해 붙입니다.

되묻는 두 경우
  • 대상을 못 찾음 — 말한 절이나 값이 문서에 없습니다. 후보를 최대 3개까지 보여줍니다.
  • 대상이 여럿 — 바꿀 현재 값이 그 절 안에 여러 개라 무엇을 가리키는지 확정할 수 없습니다.
어떻게 답하나
  • 되물음 블록은 버튼이 아닙니다. 답은 다시 [No · 변경 요청]을 눌러 더 구체적으로 적어 주면 됩니다.
  • 되묻기는 2번까지입니다. 그 뒤에는 해당 의견을 "대상 미확인"으로 정리하고 더 붙잡지 않습니다.
  • 되묻기만 하고 아무것도 고치지 못한 라운드는 라운드 수를 소모하지 않습니다.

07

이 봇이 하지 않는 것

자동 머지
  • 봇이 스스로 머지하는 경로는 없습니다. 사람이 승인 버튼을 누른 경우에만 머지 API를 호출합니다.
  • AI 요약은 읽는 것을 돕는 자료일 뿐, 판단을 대신하지 않습니다.
머지 차단
  • [No · 변경 요청]은 GitLab에서 머지를 막지 않습니다. GitLab REST API에 버전 독립적인 "변경 요청" 상태가 없기 때문입니다.
  • 차단이 필요하면 GitLab 승인 규칙을 따로 설정해야 합니다.
코드 품질 심사
  • 보안 취약점 탐지나 코드 품질 등급을 매기는 도구가 아닙니다.
  • mrdoc은 무엇이 바뀌었는지 서술할 뿐, 좋다/나쁘다를 판정하지 않습니다 — 평가 어휘 자체가 금지되어 있습니다.
08

지금 어디까지 와 있나

기능은 전부 기본이 꺼져 있고 하나씩 켜는 구조입니다. 도입할 때는 아래 순서로 단계를 올리면서 각 단계가 안정된 뒤 다음을 켜는 방식을 권합니다.

단계기본값켜면 생기는 일
알림 + 버튼항상 MR 알림, 승인·의견 버튼. 여기까지는 LLM 없이 동작합니다
AI 요약켜짐 알림에 요약과 주요 변경점이 붙습니다. 실패하면 요약 없이 알림만 갑니다
실제 수정(리바이스)꺼짐 의견이 커밋·푸시로 이어집니다. 저장소에 쓰기가 발생하는 첫 단계입니다
mrdoc 리포트꺼짐 문서 MR에 검증된 변경 리포트가 붙습니다. 별도 토글이 하나 더 있습니다
폴러 · 소켓 모드꺼짐 웹훅을 놓친 경우의 보완 경로. 필요할 때만 켭니다

미리 알고 있어야 할 한계

재발급된 승인 버튼 알림 후 작성자가 push하면 봇이 승인 버튼을 새로 발급하는데, 이 버튼은 현재 정상 동작하지 않습니다. 그 경우 GitLab에서 직접 머지하거나, MR을 다시 열어 새 알림을 받으세요.
비용 상한은 아직 안 걸린다 LLM 호출 비용 상한값을 설정할 수는 있지만 실제로 집행되지 않습니다. 비용 통제는 현재 시간 제한(호출당 상한)으로만 이루어집니다.
재시작하면 진행 중 작업이 끊긴다 수정 작업 도중 서버가 재시작되면 그 작업은 이어지지 않고, 일정 시간 뒤 수동 처리로 전환됩니다. 그때는 사람이 이어받으면 됩니다.
