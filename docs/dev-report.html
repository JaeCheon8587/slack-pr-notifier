01

워크플로우

미들웨어(FastAPI + SQLite)가 GitLab과 Slack 사이에서 상태·승인·머지·AI 재생성을 모두 전담한다. GitLab은 호스트 인바운드가 방화벽으로 막혀 폴링(아웃바운드)으로 수집하고, Slack 액션만 인바운드로 받는다. 두 수집 레일은 코드에 모두 있고 동일한 app/ingest.py 핸들러를 공유한다 — 웹훅 라우트(/webhooks/gitlab/mr)는 항상 등록되고, 폴러는 POLL_ENABLED + POLL_PROJECT_IDS가 설정된 배포에서만 기동하는 옵트인 경로다(코드 기본값은 off).

상태 기계 — 5상태 CAS

모든 전이는 단일 원자적 CAS 문 UPDATE review_session SET status=? WHERE id=? AND status=?로 수행된다. rowcount=0이면 전이 거부(check-then-act 아님).

인프라/회복 계층

앱 기동(lifespan)에서 start_* 4개를 무조건 호출하지만, 실제로 항상 뜨는 데몬 스레드는 스위퍼·notify 큐 2개다. 폴러와 Socket Mode는 각자의 설정 게이트가 꺼져 있으면 start_*가 그대로 no-op으로 반환한다.
  • 타임아웃 스위퍼 — merging/revising 세션이 *_since 임계 초과 시 manual로 CAS 수렴 (60s 주기, 상시 기동)
  • notify 재시도 큐 — 선형 백오프(30s × attempts, 최대 5회)로 재시도하고 event_log.send_state(pending/sent/failed)로 추적 · 프로세스 재시작 시 pending 행을 다시 적재 (상시 기동). 단 현재 사용처는 스위퍼의 manual 전환 통지 한 곳뿐이며, 나머지 Slack 발송(최초 알림·버튼 회수·라운드 재알림)은 이 큐를 거치지 않고 직접 호출한다
  • GitLab 폴러 — 방화벽 차단 환경을 위한 주 수집경로로 구현된 옵트인 워커(POLL_ENABLED와 POLL_PROJECT_IDS가 모두 있어야 기동, 주기 기본 60s). opened MR 신규 감지·사람 push·외부 머지/닫힘·외부 닫힘 후 재오픈(mr_reopened)까지 모두 폴링으로 감지하고 동일한 ingest 핸들러로 분기
  • Slack Socket Mode — 인바운드 HTTP가 막힌 환경의 아웃바운드 전용 WebSocket 폴백. SLACK_SOCKET_MODE + SLACK_APP_TOKEN이 있어야 연결하며, 스레드는 자체 루프가 아니라 slack_sdk 클라이언트가 관리한다 (HTTP 라우트와 동일한 dispatch_interaction 재사용)
02

변경된 부분

원래 설계 문서(docs/mr-review-pipeline.html)와 비교해, 구현 과정에서 의도적으로 바꾼 지점들이다. 대부분은 "외부 의존성·권한을 줄이고 인프라를 먼저 확정하자"는 방향의 결정이다.

항목설계 원안실제 구현변경 배경
MR 수집 경로 설계GitLab 웹훅 수신(/webhooks/gitlab/mr) — open/update/merge/close·push 이벤트 구현GitLab 폴링(아웃바운드, API 주기 조회)을 주 경로로 추가. 웹훅 라우트는 그대로 등록돼 있고, 폴러는 POLL_ENABLED 게이트로 켜는 옵트인(코드 기본값 off) 호스트 인바운드가 방화벽으로 차단돼 웹훅 수신 불가 → 폴러로 전환. 두 레일은 같은 ingest 핸들러 공유

GitLab 라벨 설계5-상태 라벨(docs-review/revise/merging/approved/manual) + docs-revise-N round 라벨 미러링 구현GitLab 노트로 결정·의견만 미러 (라벨 API 미사용) 봇의 라벨 권한·티어 의존성 제거. DB가 단일 원본

의견 모달 설계확인질문 체크박스 + 자유 텍스트 구현자유 텍스트만 (question_refs 컬럼은 유지하되 항상 NULL) 확인질문 생성 기능 미구현. 컬럼은 복원 대비 보존
재알림 방식 설계기존 스레드 메시지 갱신 구현라운드마다 새 메시지(chat.postMessage) 발송 후 slack_ts 이동 리뷰어가 각 라운드를 별도로 추적·비교하기 쉽도록
재알림 내용 설계라운드 번호·SHA·미반영 의견 구현+ 변경 파일 통계 · AI 요약 · GitLab compare 링크 (추가) 승인 판단을 메시지만으로 가능하게 (실환경 검증 완료)

03

고도화 필요 부분

인프라(상태기계·CAS·머지·직렬화·회복 계층)를 먼저 확정하느라 AI 영역은 최소 동작으로 넘겼다. 아래는 실서비스 전에 다뤄야 할 항목이다.

AI 리뷰어 — 문서 특화 분석 AI

app/ai_reviewer.py · review-prep [A]

현재 범용 코드 리뷰(summary / key_changes / points_to_watch — "버그·부작용·테스트 누락" 관점)만 한다. 문서 MR 관점의 분석이 빠져 있다.

  • 문서별 변경 등급 판정 (주장 변경 / 보강 / 표현만) — 리뷰어가 어디를 깊이 볼지 가이드
  • 확인질문 자동 생성 — 현재 모달 체크박스와 연결된 question_refs가 항상 NULL
  • 변경 동인·서술 이동·독자 영향 분석 (설계가 묘사하던 리뷰 자료의 본질)

AI 러너 — revise 체인 고도화 AI

app/ai_runner.py · revise 러너 [B]

현재 기본값이 StubRunner(파일 변경 0, 모든 의견 "AI 체인(P5) 미구현"으로 미반영). AI_RUNNER=claude 설정 시 ClaudeCliRunner(단일 CLI 호출)가 동작하지만, 설계가 묘사한 다단 체인은 아니다.

  • 기본 러너 전환 — 프로덕션에선 claude 러너가 기본이 되어야 revise가 실제로 일어남
  • 3단 오케스트레이터 체인 — 메타프롬프팅(3a) → 재생성(3b) → 대조검증(3c) 서브에이전트 분리 미구현. 현재는 단일 호출 1회
  • 자기 채점 방지 — 3c 검증을 fresh-context 서브에이전트로 분리(현재 없음)
  • 원인 분류 재시도 라우팅 — 미반영 시 구현 누락→3b / 스펙 모호→3a 재투입 (라운드당 2회 한정). 현재 없음
  • cross-doc 정합성 워커 — 문서 경계를 넘는 의견 처리 분기 미구현

리뷰 산출물 — report.html + 스레드 파일 링크 설계 미구현

app/ai_reviewer.py · app/slack_client.py (ai_review_blocks · _revise_result_payload)

설계 원안은 claude가 report.html을 생성하고 Slack 스레드에 파일 다운로드 링크를 붙이는 것이었다. 현재는 AI 요약을 Slack 인라인 블록으로만 렌더하며, 파일 업로드 API(files.*)도 스레드 회신(thread_ts)도 코드 어디에서도 호출하지 않는다 — 양쪽 다 미구현이다.

  • 길이 상한에 걸린다 — AI 요약 블록은 2900자에서 절단되고(Slack section 3000자 제한), 라운드 재알림은 요약 700자·diff stat 12줄/900자로 잘린다. MR이 클수록 근거가 사라진 요약만 남는다
  • 산출물 생성 경로 부재 — review-prep [A]는 구조화 JSON(summary/key_changes/points_to_watch)만 반환한다. HTML 문서를 만드는 단계 자체가 없다
  • Slack 업로드 배선 — files.getUploadURLExternal → files.completeUploadExternal 2단계 호출과 thread_ts 스레드 회신을 새로 붙여야 한다. 봇에 files:write 스코프 추가 필요
  • 보관·노출 정책 — 생성한 report.html을 어디에 얼마나 보관할지, 채널 밖으로 새지 않게 할지 결정 필요 (compare 링크에 적용한 자격증명 살균과 같은 급의 검토)

재발급 승인 버튼 — 실동작 결함 BUG

app/ingest.py · _reissue_approve_button

사람 push 후 reviewing 세션은 [승인] 버튼만 재발급하지만, 토큰에 title/url/head_ref/... 빈 문자열이 들어간다. 이 토큰은 app/slack_dispatch.py의 _decode_mr가 요구하는 "모든 필드 truthy" 검사에서 거부돼 클릭해도 작동하지 않는다. 코드 주석(RISKS)에도 "따라가야 할 단계"로 표기돼 있다 — 다만 그 주석이 가리키는 경로는 app.slack_actions._decode_mr로, dispatch 분리 이후 갱신되지 않았다.

  • metadata 소스 확보 — GitLab API fetch로 title/url/branch 채우기, 또는 스키마 확장(head_ref 등 컬럼 추가)

운영 튜닝·표현 보강 기타

동작에는 문제가 없으나, 실운영에서 마주칠 수 있는 후속 항목이다.

  • 하드코딩 상수의 config 노출 — app/slack_dispatch.py의 ROUND_CAP=3·POLL_INTERVAL_SECONDS=3·POLL_MAX_ATTEMPTS=10(머지 poll)이 config에 없이 코드에 고정. app/config.py로 이관하되, 폴러의 POLL_INTERVAL(60s)과 이름이 겹치므로 구분할 것
  • GitLab 라벨 미러링 복귀 — GitLab UI에서 상태·라운드를 보려면 라벨이 유용. 필요 시 라벨 권한 확보 후 재도입
  • HTML→PNG 스크린샷 — Slack 인라인 렌더용 (설계 v2 옵션)
