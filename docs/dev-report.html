01

워크플로우

미들웨어(FastAPI + SQLite)가 GitLab과 Slack 사이에서 상태·승인·머지·AI 재생성을 모두 전담한다. GitLab은 호스트 인바운드가 방화벽으로 막혀 폴링(아웃바운드)으로 수집하고, Slack 액션만 인바운드로 받는다. 두 수집 레일은 코드에 모두 있고 동일한 app/ingest.py 핸들러를 공유한다 — 웹훅 라우트(/webhooks/gitlab/mr)는 항상 등록되고, 폴러는 POLL_ENABLED + POLL_PROJECT_IDS가 설정된 배포에서만 기동하는 옵트인 경로다(코드 기본값은 off).

상태 기계 — 5상태 CAS

모든 전이는 단일 원자적 CAS 문 UPDATE review_session SET status=? WHERE id=? AND status=?로 수행된다. rowcount=0이면 전이 거부(check-then-act 아님).

reviewing
리뷰 진행 중 · [승인]/[의견] 버튼 활성
→ merging 승인 클릭 → revising 의견 제출 → merged 외부 머지 → manual 가드 거부 / 외부 닫힘
merging
승인 접수 · 머지 poll 진행 중 (merging_since 타임아웃 300s)
→ merged poll 성공 / 외부 머지 → manual poll 실패 · 사람 push · 외부 닫힘
revising
완전 동결 · revise 실행기 진행 중 (revising_since 타임아웃 3000s)
→ reviewing revise 성공 (round+1, attempts 리셋 · 되물음만 있고 커밋 없으면 round 유지) → manual 사람 push · 타임아웃 · attempts≥2 · 외부 닫힘 → merged 외부 머지
manual
사람 개입 대기 · 자동 동작 정지
→ merged 사람 직접 머지 → reviewing 외부 닫힘 후 재오픈 (폴러 mr_reopened) → reviewing operator_resume — 엣지 정의만 있고 호출부 없음
merged
종단 상태 — 유출 엣지 없음

인프라/회복 계층

앱 기동(lifespan)에서 start_* 4개를 무조건 호출하지만, 실제로 항상 뜨는 데몬 스레드는 스위퍼·notify 큐 2개다. 폴러와 Socket Mode는 각자의 설정 게이트가 꺼져 있으면 start_*가 그대로 no-op으로 반환한다.
  • 타임아웃 스위퍼 — merging/revising 세션이 *_since 임계 초과 시 manual로 CAS 수렴 (60s 주기, 상시 기동)
  • notify 재시도 큐 — 선형 백오프(30s × attempts, 최대 5회)로 재시도하고 event_log.send_state(pending/sent/failed)로 추적 · 프로세스 재시작 시 pending 행을 다시 적재 (상시 기동). 단 현재 사용처는 스위퍼의 manual 전환 통지 한 곳뿐이며, 나머지 Slack 발송(최초 알림·버튼 회수·라운드 재알림·report.html 업로드·mrdoc 스레드 회신)은 이 큐를 거치지 않고 직접 호출한다 — 실패는 로그만 남는다
  • GitLab 폴러 — 방화벽 차단 환경을 위한 주 수집경로로 구현된 옵트인 워커(POLL_ENABLED와 POLL_PROJECT_IDS가 모두 있어야 기동, 주기 기본 60s). opened MR 신규 감지·사람 push·외부 머지/닫힘·외부 닫힘 후 재오픈(mr_reopened)까지 모두 폴링으로 감지하고 동일한 ingest 핸들러로 분기
  • Slack Socket Mode — 인바운드 HTTP가 막힌 환경의 아웃바운드 전용 WebSocket 폴백. SLACK_SOCKET_MODE + SLACK_APP_TOKEN이 있어야 연결하며, 스레드는 자체 루프가 아니라 slack_sdk 클라이언트가 관리한다 (HTTP 라우트와 동일한 dispatch_interaction 재사용)
02

변경된 부분

원래 설계 문서(docs/mr-review-pipeline.html)와 비교해, 구현 과정에서 의도적으로 바꾼 지점들이다. 대부분은 "외부 의존성·권한을 줄이고 인프라를 먼저 확정하자"는 방향의 결정이다.

항목설계 원안실제 구현변경 배경
MR 수집 경로 설계GitLab 웹훅 수신(/webhooks/gitlab/mr) — open/update/merge/close·push 이벤트 구현GitLab 폴링(아웃바운드, API 주기 조회)을 주 경로로 추가. 웹훅 라우트는 그대로 등록돼 있고, 폴러는 POLL_ENABLED 게이트로 켜는 옵트인(코드 기본값 off) 호스트 인바운드가 방화벽으로 차단돼 웹훅 수신 불가 → 폴러로 전환. 두 레일은 같은 ingest 핸들러 공유
리뷰 산출물 설계claude가 report.html 생성 → Slack 스레드에 파일 다운로드 링크 구현AI 요약 인라인 Slack 블록 + 미들웨어가 report.html(AI 요약 + diff)을 렌더해 reports/에 보관하고 알림 스레드에 파일 첨부. md 위주 MR 은 mrdoc 이 mrdoc-report.html로 대신한다 생성 주체를 claude 에서 결정론 렌더러로 옮겼다. 인라인 블록은 길이 상한에 잘리므로 전문은 파일로 — 업로드는 best-effort 라 실패해도 알림은 유효
GitLab 라벨 설계5-상태 라벨(docs-review/revise/merging/approved/manual) + docs-revise-N round 라벨 미러링 구현GitLab 노트로 결정·의견만 미러 (라벨 API 미사용) 봇의 라벨 권한·티어 의존성 제거. DB가 단일 원본
Slack permalink 설계Slack permalink를 MR 코멘트로 미러링 구현미구현 (결정 노트 미러로 대체) 추가 호출 대비 효용 낮아 보류
AI 리뷰 성격 설계문서 특화 등급(🔴주장변경/🟡보강/🟢표현만) + 확인질문 리스트 구현범용 코드 리뷰(summary/key_changes/points_to_watch) + 옵트인 mrdoc — 문서 MR 변경을 구조 · 의미(맥락) · 의미(값) · 표현 · 미분류로 분류한 매트릭스 리포트. 확인질문은 없음 등급을 LLM 판단 대신 도구가 증명하는 사실(구조 diff · 리터럴 차집합)과 검증된 분류로 세웠다 — 축이 설계의 3등급과 다르다(docs/mrdoc-pipeline.html)
revise 실행 구조 설계claude 단일 세션(호출 1회) 안에서 3a · 3b · 3c 서브에이전트 오케스트레이션, 단계별 별도 CLI 호출 금지 구현AI_RUNNER=staged — 단계마다 별도 codex exec 호출 3회 + Python 결정론 노드 5개, 진행은 산출물 파일 존재로 판정(옵트인, 기본은 stub) headless 서브에이전트 결과 회수가 종료 코드 0인 채 조용히 실패(실측) → 실패가 보이는 구조로. mrdoc 과 같은 방식(docs/revise-workflow.html)
되물음 설계없음 — 모든 라운드가 round 를 소모 구현대상을 못 찾거나 바꿀 현재 값이 여럿이면 질문 + 후보를 재알림에 싣고, 커밋이 없으면 round 유지(세션당 2회) 사람이 가리킨 곳이 문서에 없을 때 지어내서 고치는 대신 되묻는다. 새 상태 없이 기존 레일을 탄다
의견 모달 설계확인질문 체크박스 + 자유 텍스트 구현자유 텍스트만 (question_refs 컬럼은 유지하되 항상 NULL) 확인질문 생성 기능 미구현. 컬럼은 복원 대비 보존
재알림 방식 설계기존 스레드 메시지 갱신 구현라운드마다 새 메시지(chat.postMessage) 발송 후 slack_ts 이동 리뷰어가 각 라운드를 별도로 추적·비교하기 쉽도록
재알림 내용 설계라운드 번호·SHA·미반영 의견 구현+ 변경 파일 통계 · AI 요약 · GitLab compare 링크 · 되물음 질문 + 후보 · 라운드 report.html 첨부 (추가) 승인 판단을 메시지만으로 가능하게 (실환경 검증 완료)
manual→reviewing 설계"미구현 백로그"로 표기 구현폴러가 외부 닫힘 후 재오픈 자동 복귀(mr_reopened) 구현 무한 재알림 방지 가드와 함께 안전하게 구현 가능했음
이 표의 "변경 배경"은 어느 쪽이 맞다는 뜻이 아니라, 구현 과정에서 내린 취사선택이다. 남은 문서 특화 영역(확인질문 · mrdoc 기본 활성화)은 §3 고도화 항목에서 다시 다룬다.
03

고도화 필요 부분

인프라(상태기계·CAS·머지·직렬화·회복 계층)를 먼저 확정한 뒤 AI 영역을 두 레일(mrdoc · StagedRunner)로 채웠다. 둘 다 옵트인이고 실호출 검증이 남아 있다. 아래는 실서비스 전에 다뤄야 할 항목이다.

AI 리뷰어 — 문서 특화 분석 AI · 부분 구현

app/ai_reviewer.py · review-prep [A] · app/mrdoc/ · mrdoc 레일 [C]

범용 리뷰어 [A]는 여전히 범용 코드 리뷰(summary / key_changes / points_to_watch)만 한다. 문서 MR 은 옵트인 mrdoc 레일이 결정론 도구 + codex exec 위성 3개(analysis · verifier · themes)로 변경을 구조 · 의미(맥락) · 의미(값) · 표현 · 미분류로 분류하고, 주요 주제 · 확인이 필요한 항목 · 파일별 상세를 담은 매트릭스 리포트를 스레드에 올린다.

  • mrdoc 기본 활성화 — MRDOC_ENABLED · MRDOC_SATELLITE_ENABLED 모두 기본 false. 켜려면 호스트에 codex CLI 가 필요하다
  • revise 뒤 mrdoc 재실행 없음 — 라운드 재알림은 범용 3슬롯 리포트이고, 문서 MR 의 매트릭스 리포트는 첫 리뷰 것 그대로다
  • 확인질문 자동 생성 — 미구현. 모달 체크박스와 연결될 question_refs가 항상 NULL
  • 등급 축 — mrdoc 의 성질 분류는 설계의 주장 변경 / 보강 / 표현만 3등급과 축이 다르다. 어느 쪽을 리뷰어 가이드로 쓸지 정하지 않았다

  • 원인 분류 재시도 라우팅 — 구현: 스펙 반려 → 3a, 리터럴 미치환 → 3b, 3c 미반영 → 3b 다음 3a (라운드당 2회)

  • codex 샌드박스 한계 — 도구별 차단이 없어 「3a 는 목차만 · 3c 는 diff 만」이 프롬프트 규칙에만 기댄다
