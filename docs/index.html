Slack MR Notifier — 문서 안내

GitLab Merge Request가 열리면 Slack으로 리뷰를 요청하고, 버튼 하나로 승인하거나 의견을 남기면 LLM이 실제로 문서·코드를 고쳐 push하고 다시 알리는 미들웨어입니다. 문서(md) 위주의 MR은 mrdoc 레일로 빠져, 무엇이 어떻게 바뀌었는지를 검증된 HTML 리포트로 만들어 같은 스레드에 붙입니다. 이 페이지는 어느 문서부터 읽을지를 정해 주는 진입점입니다.

v1 최종 갱신 2026-09-28 브랜치 feature/python-middleware 문서 안내 5 · 심화 5

모든 MR은 같은 입구로 들어와 하나의 Slack 메시지가 됩니다. 거기서부터 사람이 무엇을 눌렀는가와 바뀐 파일이 문서인가에 따라 길이 갈립니다.

03

문서 지도

안내 문서는 요약과 판단 근거까지만 담고, 상세 규격은 심화 문서가 갖습니다. 두 설명이 어긋나면 심화 문서가 옳습니다.

문서독자성격 권위담고 있는 것
index 현재 전원진입— 읽기 경로와 문서 지도
overview 전원소개요약 무엇을 해주나 · 리뷰어가 보는 화면 3컷 · 되물음 · 리포트 읽는 법 · 안 하는 것
architecture 개발자개념요약 스택 선택 · 엔트리포인트 · 레일 분기 · 상태기계 · 데이터 · 두 레일 요약
trust-model 전원개념요약 LLM을 믿지 않는 설계 — 파싱이 검증, 숫자는 코드가 셈, 결정론 게이트, 실패는 강등
setup 운영자절차권위 설치 · 환경변수 전수 · 웹훅/Slack App 등록 · 운영 · 알려진 결함
mr-review-pipeline 개발자스펙권위 컴포넌트 맵 · 메인 플로우 · 상태기계 · SQLite 스키마 · 장애 모드
revise-workflow 개발자스펙권위 리바이스 8노드 DAG · 스펙 게이트 · 결정론 게이트 · 재투입 예산 · 노드별 템플릿
mrdoc-pipeline 개발자스펙권위 mrdoc 10노드 DAG · 위성 규약 · 산출물 소비 관계 · 노드별 템플릿
mrdoc-report-template 전원샘플실물 실제 MR로 렌더한 리포트 한 벌. 사용자가 받는 산출물의 모습
dev-report 이해관계자보고시점 구현 진척 · 변경된 부분 · 고도화가 필요한 부분
읽는 순서가 중요한 이유 심화 3종은 각각 800~1700줄짜리 규격서입니다. 제품이 뭘 하는지 모르는 상태에서 열면 템플릿 원문에 파묻힙니다. 안내 문서를 먼저 통과하세요.
권위 구분 안내 문서와 심화 문서의 설명이 어긋나면 심화 문서가 옳습니다. 단, 설정값만은 setup이 권위입니다 — 코드에서 직접 확인해 갱신합니다.
04

이 문서들을 고칠 때

권위는 심화 문서에 있다
중복 서술 금지
  • 노드 목록, 템플릿, 필드 규격은 심화 문서에만 적습니다.
  • 안내 문서는 요약과 "왜 그렇게 했는가"까지만 담고, 각 절 끝의 더 깊이 블록으로 심화 문서의 해당 절에 넘깁니다.
  • 같은 사실을 두 곳에 쓰면 반드시 한쪽이 낡습니다.
코드에서 확인한 것만 쓴다
기본값 · 경로 · 상한
  • 환경변수 기본값은 app/config.py, 라우트 경로는 app/main.py와 대조한 값만 적습니다.
  • 기억에 의존해 적힌 수치가 이 저장소 문서를 낡게 만든 주범입니다.
형식을 맞춘다
스타일 셸 공유
  • 안내 문서 5종은 assets/doc.css를 링크합니다. 인라인 <style>을 새로 만들지 않습니다.
  • 심화 5종은 각자의 인라인 스타일을 유지합니다 — 건드리지 않습니다.
  • 제목에 버전을 표기하고, 문서 끝에 개정 이력을 남깁니다.
