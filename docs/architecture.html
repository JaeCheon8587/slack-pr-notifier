Docs · Architecture

시스템 한 장 — 스택 · 상태 · 두 레일

코드를 읽기 전에 어디에 무엇이 있고 왜 그렇게 두었는지를 잡아 두는 문서입니다. 노드별 필드 규격이나 템플릿 원문은 여기 없습니다 — 각 절 끝의 더 깊이에서 권위 문서로 넘어가세요. 제품이 뭘 하는지 아직 모른다면 overview를 먼저 읽는 편이 빠릅니다.

v1 최종 갱신 2026-09-28 독자 합류 개발자 성격 개념 · 요약
01

스택 — 없는 것이 더 많다

이 프로젝트의 첫인상은 무엇을 쓰지 않았는가입니다. ORM도, 작업 큐 미들웨어도, 캐시 서버도 없습니다. 의도적인 선택입니다.

쓰는 것
전부 표준 라이브러리에 가깝다
  • FastAPI + uvicorn, 워커 1개
  • stdlib sqlite3 — WAL 모드, busy_timeout 설정
  • 백그라운드는 데몬 스레드 + queue.Queue
  • 외부 호출은 httpx 직접 — Slack SDK도 쓰지 않음
안 쓰는 것
그리고 그 대가
  • ORM 없음 → 스키마가 app/db.py 한 곳에 SQL로 고정. 마이그레이션 도구가 없으니 스키마 변경 비용이 큽니다.
  • Celery/Redis 없음 → 배포가 프로세스 하나로 끝납니다. 대신 재시작하면 진행 중이던 작업이 사라집니다.
  • 워커 1개 → 프로세스 간 락을 고민할 필요가 없습니다. 수평 확장은 불가능합니다.
이 선택이 만든 설계
제약이 구조를 결정했다
  • 큐를 믿을 수 없으니 상태를 DB와 파일에 둡니다. 그래서 파이프라인이 재개 가능합니다.
  • 분산 락이 없으니 SQL의 UPDATE … WHERE status=? 자체를 락으로 씁니다.
  • 재시도 인프라가 없으니 타임아웃을 계층으로 겹쳐 놓았습니다.
02

기동되는 것 — 엔트리포인트

app/main.py의 lifespan이 기동 시 넷을 켜고 종료 시 역순으로 끕니다. 나머지는 HTTP 라우터이거나 필요할 때 시작되는 워커입니다. 대부분 기본이 꺼져 있고, 각자의 설정 게이트가 닫혀 있으면 호출해도 아무 일이 없습니다.

무엇파일기본역할
GitLab 웹훅gitlab_webhook.py항상 POST /webhooks/gitlab/mr — MR open/reopen/merge/close, push 수신
Slack 인터랙션slack_actions.py항상 POST /webhooks/slack/actions — 버튼 클릭과 모달 제출
healthmain.py항상 GET /health
스위퍼sweeper.py켜짐 제한 시간을 넘긴 merging/revising 세션을 수동으로 내림
알림 아웃박스notify_queue.py켜짐 Slack 전송 실패를 재시도. 기동 시 미발송 건을 다시 큐에 넣음
GitLab 폴러gitlab_poller.py꺼짐 웹훅을 놓쳤을 때의 보완 경로. 외부 머지·재오픈·사람 push를 따라잡음
Socket Modeslack_socket.py꺼짐 공개 URL 없이 Slack 이벤트를 받는 경로
리바이스 워커revise_executor.py요청 시 의견이 들어오면 시작되는 단일 데몬 스레드. 동시 실행은 하나뿐
읽는 순서 app/main.py → app/gitlab_webhook.py → app/ingest.py → app/slack_dispatch.py 순으로 읽으면 한 MR이 알림이 되고 버튼 클릭이 처리되기까지를 한 줄로 따라갈 수 있습니다.
03

레일이 갈리는 곳

MR 하나는 항상 같은 입구로 들어와 Slack 메시지 한 통이 됩니다. 그 직후 app/mrdoc/rail.py의 게이트가 변경 파일 중 md 비중을 재고, 기준(mrdoc_doc_ratio_threshold, 기본 0.8) 이상이면 mrdoc이 인수합니다.

일반 레일
모든 MR의 기본값
  • AI 요약 + 버튼 알림
  • 범용 리뷰 리포트(report_html.py)를 스레드에 첨부
  • 의견이 오면 리바이스 8노드가 실제 수정을 수행
mrdoc 레일
문서가 지배적인 MR
  • 게이트 통과 시 범용 리포트를 억제하고 mrdoc이 리포트를 담당
  • 10노드 파이프라인이 별도 작업 디렉터리에서 돌아감
  • 리바이스 루프는 그대로 동작 — 라운드가 끝나 HEAD가 움직이면 mrdoc이 다시 리포트를 만듭니다
둘 다 켜야 동작한다 mrdoc은 토글이 둘입니다 — 레일 자체(mrdoc_enabled)와 LLM 위성(mrdoc_satellite_enabled). 둘 다 켜져야 mrdoc이 리포트를 "인수"하며, 한쪽만 켜면 범용 리포트가 그대로 나갑니다.
04

상태기계 — 다섯 상태

MR 하나당 review_session 한 행이고, 그 행의 status가 시스템의 진실입니다. 상태는 다섯 개뿐이며 merged는 종단입니다.

reviewing알림 게시됨 · 버튼 대기
merging머지 진행 · 결과 폴링 중
revising수정 작업 중 · 세션 잠김
manual봇이 손 뗌 · 사람이 이어받음
merged종단

전이는 목록에 있는 것만

app/state_machine.py의 ALLOWED_TRANSITIONS가 (출발, 도착) 쌍마다 허용되는 사유까지 고정합니다. 목록에 없는 전이는 예외이고, 허용되지 않은 사유를 붙여도 예외입니다. 새 전이를 코드로 몰래 만들 수 없습니다.

전이허용 사유의미
reviewing → mergingapprove 승인 버튼이 모든 검사를 통과
reviewing → revisingopinion 의견 제출 — 이 전이가 곧 세션 잠금
reviewing → mergedexternal_merge 봇 밖에서 사람이 머지함
reviewing → manualexternal_close · guard_reject MR이 닫혔거나, 승인자 매핑이 없어 거절
merging → mergedmerge_poll_success · external_merge 머지 확인됨
merging → manualmerge_poll_failed · push_during_merge · external_close 머지 확인 실패, 또는 도중에 push/close가 끼어듦
revising → reviewingrevise_success 라운드 성공 — 다시 사람의 판단으로
revising → manualhuman_push · revise_timeout · revise_attempts_exceeded · external_close 사람이 직접 push했거나, 시간·시도 한계
revising → mergedexternal_merge 작업 중 밖에서 머지됨
manual → mergedhuman_merge 사람이 마무리
manual → reviewingmr_reopened · operator_resume 닫혔던 MR이 다시 열림. 폴러만 호출하며, 직전 이벤트가 external_close일 때로 제한

CAS가 곧 락이다

어떻게 동작하나
  • 전이는 단일 문장입니다 — UPDATE review_session SET status=? WHERE id=? AND status=?
  • 성공하면 rowcount 1, 이미 남이 옮겼으면 0입니다.
  • 0을 받은 쪽은 졌다고 판단하고 아무 부수효과도 남기지 않습니다.
이것이 막아 주는 것
  • 중복 클릭 — 두 번째 승인은 rowcount 0으로 조용히 무시됩니다.
  • 경합 — 승인 클릭과 외부 머지 웹훅이 동시에 와도 하나만 이깁니다.
  • 별도 락 테이블도, 분산 락도 필요 없습니다. 문장이 락입니다.
상태 기계 · 이중 기록 · 장애 모드
05

데이터 — 테이블 셋

SQLite 하나에 테이블 셋이 전부입니다. 각 테이블의 UNIQUE 제약이 곧 이 시스템의 중복 방지 장치이므로, 스키마를 읽을 때 제약부터 보세요.

review_session
MR 하나 = 행 하나
  • UNIQUE(project_id, mr_iid) — 같은 MR로 세션이 둘 생기지 않습니다.
  • status는 다섯 값으로 CHECK 제약
  • round, revise_attempts, merging_since, revising_since, slack_channel, slack_ts, mr_sha
  • 브랜치·제목·URL 컬럼이 없습니다. 이 생략이 뒤에 나오는 "재발급 버튼" 결함의 근본 원인입니다.
opinion
리뷰어가 넣은 의견
  • UNIQUE(session_id, slack_user, body_hash) — 같은 사람이 같은 말을 또 넣어도 한 건입니다.
  • applied_round — 몇 라운드에서 처리됐는지. 값이 차면 대기열에서 빠집니다.
  • last_verdict — 반영되지 않았다면 그 이유
event_log
한 테이블이 네 가지 일을 한다
  • 멱등 원장 — UNIQUE(idempotency_key) 위반이 곧 중복 차단
  • 락 시계 — 의견 잠금 시각의 기준점
  • 되물음 카운터 — clarify 행을 세어 한도를 판단
  • Slack 아웃박스 — send_state로 발송 재시도를 관리

중복을 막는 네 가지 키

무엇의 중복키동작
웹훅 재전송GitLab 웹훅 UUID 같은 UUID면 삽입이 실패하고 그대로 종료. 헤더가 없으면 통과시킵니다
같은 의견 재제출본문 정규화 해시 공백·형식 차이를 없앤 뒤 해시해 비교
승인 중복 클릭CAS 그 자체 별도 키 없이 상태 전이 실패로 걸러집니다
Slack 재전송event_log 행 id 아웃박스가 행 단위로 발송 상태를 관리

타이머는 겹쳐 놓았다

불변식 큐 대기 한도 < 작업 벽시계 한도 < 세션 타임아웃 (기본 600 < 2400 < 3000초). 안쪽이 먼저 끊겨야 바깥이 이유를 알고 정리할 수 있습니다. 이 순서가 뒤집히면 스위퍼가 살아 있는 작업을 죽입니다. 설정을 바꿀 때 반드시 함께 검토하세요.

리바이스 레일 — 8노드

의견 하나가 커밋이 되기까지의 사슬입니다. 일직선 체인이고, 각 노드는 파일 하나를 남깁니다. 파일 이름의 숫자가 곧 순서입니다.

3spec15-spec.md— 스펙 게이트. 편집 전에 요구를 원문과 대조
4impact20-impact.md— 같이 손봐야 할 곳을 산출

6gate35-gate.md— 요구한 값이 정말 들어갔는지 기계적으로 확인. 실패하면 되돌립니다
7verify40-verify.md● 의견별로 반영 여부를 대조검증

아티팩트가 곧 상태다
  • 진행 상태를 따로 기록하지 않습니다. 어떤 파일이 있느냐로 상태를 도출합니다.
  • 그래서 gate에서 죽은 라운드는 다시 돌리면 gate부터 재개됩니다.
  • 한 바퀴 돌았는데 상태가 그대로면 "진전 없음"으로 판단해 멈춥니다 — 무한 루프가 구조적으로 불가능합니다.
재투입 예산
  • 라운드당 2회까지만 되돌려 다시 시킵니다.
  • 원인별로 돌아가는 지점이 다릅니다 — 스펙 반려는 intent로, 값 미반영은 edit으로.
  • 횟수는 이력 파일에서 세므로, 중간에 재시작해도 예산이 초기화되지 않습니다.
라운드 회계
  • 의견 제출은 3라운드까지 (ROUND_CAP).
  • 되물음만 하고 커밋이 없으면 라운드를 소모하지 않습니다.
  • 되묻기는 2회까지. 넘으면 해당 의견을 "대상 미확인"으로 종결합니다.

원자 인벤토리
숫자의 단일 출처
  • 모든 셀 수 있는 사실을 원자 하나로 환원합니다 — (유닛, 파일, 축, 연산, 종류).
  • 축은 구조 / 의미 / 표현, 연산은 추가 / 변경 / 삭제.
  • 이 집계 하나가 리포트 매트릭스·검증 프롬프트·주제 입력에 모두 쓰입니다. 숫자가 갈라질 자리가 없습니다.
COUNTS 게이트
산문 vs 집계
  • 검증 단계에 파일별 실측 개수를 주입하고, 서술이 주장한 개수와 대조시킵니다.
  • "n곳 vs n항목" 같은 단위 차이는 넘어가고, 존재 모순만 불일치로 칩니다 — "없다"고 했는데 원자가 있는 경우.
fix 라운드와 강등
  • 문제가 발견되면 최대 2회 다시 씁니다. 대상은 세 게이트(검증·분류·누락)의 합집합입니다.
  • 재작성이 실패하면 직전 상태로 복원하고, 소모된 라운드는 돌려주지 않습니다.
  • 주제나 검증이 실패해도 중단하지 않습니다 — 실패를 표기한 채 리포트를 냅니다.
