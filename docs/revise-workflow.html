Part 1

에이전트 — 누가 무엇을 쓰나

LLM 자리는 3개 — 구조화(3a) / 선별+편집(3b) / 대조 검증(3c). 세 자리는 각각 별도 headless 호출이고, 사이의 존재검사 · 역검색 · 게이트 · 추출은 Python 결정론 노드다. 도구 목록이 집행 수단이다 — 프롬프트로 금지하는 것과 도구를 안 주는 것은 다르다.

오케스트레이터 StagedRunnerPython—headless claude ×3 · 결정론 노드 · gitLLM 아님 — 노드 루프 + 재투입 예산만
3a INTENTheadless claudehigh없음 — --tools "", 텍스트 in/out전부 (Read · Grep · Edit · Write · Bash)

3c VERIFYheadless claudehigh없음 — --tools "", diff 가 증거의 전부 실측 개정전부 (Read 포함)
--setting-sources "" 는 선택이 아니다 실측 추가 — 없으면 실행하는 사람의 사용자 · 플러그인 설정이 매 단계 시스템 프롬프트로 딸려 들어온다. 첫 스모크는 「1+1」 수준의 프롬프트에서 예산 초과로 죽었고, stderr 에는 플러그인 SessionEnd 훅 실패만 찍혀 원인을 가렸다. 격리 후 같은 프롬프트가 가장 작은 예산 안에서 끝나고 stderr 가 비었다. 프로덕션 레일은 누구의 노트북에서 도느냐에 좌우돼선 안 된다.

  2. 산출물을 안 쓰고 성공을 반환한 노드는 abort 로 걸린다.거짓 성공이 다음 노드를 의존성 없이 깨뜨리는 대신 즉시 멈춘다

재개. 벽시계 초과로 죽어도 재큐잉 시 끝난 노드는 건너뛴다(현재는 매번 처음부터 다시 돈다). edit 재실행 직전에는 00-intent.md frontmatter 의 base_sha 로 md 경로만 되돌려 항상 깨끗한 상태에서 시작한다.

  2. search_terms는 원문에 그대로 있을 문자열만.자기가 지어낸 요약문 금지 — 이 문자열이 다음 단계에서 기계가 검증할 유일한 앵커다

  2. 판정 축은 의견 원문이다.스펙(3a 산출)은 참고용 — 3a 가 원문을 잘못 옮긴 오역도 여기서 잡힌다

  4. 판정마다 근거를 파일 · 라인 · before/after 로 지목한다.지목할 diff 가 없으면 그 의견은 applied 가 아니다
도구를 안 주는 것이 유일한 집행 수단이다 실측 개정 — 3c 는 「diff 가 증거의 전부」라고 자기 HARD LIMIT 에 적어 두고도 Read 를 들고 있었다. 같은 입력 실측: Read 有 $1.2174 / 2턴, 無 $0.0287 / 1턴, 판정은 동일. 42배를 주고 산 것이 없었다.
파이썬 오케스트레이터가 3c 판정과 3b 영수증을 대조하고 불일치 시 3c를 신뢰한다 — 워커의 「했다」는 주장이지 증거가 아니다.

Part 2

워크플로우 — 고정 DAG

7개 노드가 한 줄로 이어진 고정 사슬이다. 분기가 없고, 다음에 무엇이 도는지는 산출물 파일의 존재만으로 결정된다 (app/mrdoc/dispatch.py:87 derive_state 패턴의 축소판).

필터
#노드실행산출물하는 일

원안 8단계 → 실제 실행 단위

원안평가담당산출물
1. 의견 구조화 (코드 참고 X)⚠️ 수정LLM 3a — 본문 대신 목차00-intent.md
2. 대상 존재 검사⚠️ 담당 변경LLM → 기계 (섹션 인덱스 + 문자열 검색)10-anchor.md

4. 동반 변경 판정✅ 유지3번 결과 중 선별만 LLM. 5번과 한 호출30-edit.md

7. 변경분 추출 + 리포트⚠️ 축소추출은 mrdoc 방식, 렌더는 기존 것 재사용50-summary.md · report.html
8. 슬랙 전달✅ 유지기존 경로 그대로 (수정 불필요)—
왜 1번을 「코드 참고 X」로 두면 안 되는가. 사람의 의견은 「이 부분」 · 「여기 좀」 · 「위에 있는 그거」처럼 지시어가 많다. 아무 컨텍스트 없이 구조화하면 모델이 대상을 지어낸다. 지어낸 대상은 2번 존재 검사에서 걸리지만, 그때는 이미 무엇을 물어봐야 하는지조차 알 수 없다.
왜 2 · 3 · 4번을 LLM 에게 주면 안 되는가. 같은 결론이 docs/mrdoc-pipeline.html 에 이미 명문화돼 있다 — 「경계는 하나다 — 두 문자열의 대조로 환원되면 툴이다. 존재하나 · 개수 맞나 · 원문에 있나 · 공집합이냐 · 같냐」, 그리고 「Grep 을 아무 위성에도 주지 않는다 — 검색은 툴이 리터럴로 한다. Grep 이 있으면 LLM 이 검색어를 짓기 시작하고, 검색어 생성은 대조할 대상이 없어 검증이 불가능하다」.
왜 8단계가 LLM 8회가 아닌가. ai_max_budget_usd는 CLI 호출당 적용된다(8회 = 최대 $8/라운드) · revise_wall_clock_seconds 위에 스위퍼가 있다 · 단계마다 컨텍스트를 다시 실어 보내는 비용이 붙는다. 3회로 8단계를 전부 덮는다.

결정론 게이트 — 이 설계의 핵심

35-gate.md가 LLM 보고를 믿지 않고 기계로 확인한다. 게이트는 판정하고, 되돌린다 — 그 판정을 근거로 무엇을 커밋할지는 오케스트레이터가 정한다.

#검사방법위반 시
1경로 화이트리스트git diff --name-only 가 전부 .md/.mdx 이고 전부 앵커/동반 후보 파일 집합 안인가부분 벗어난 그 파일만 되돌린다
2리터럴 실증의견이 「A → B」 치환을 요구했다면 extract_literals 로 차집합 확인부분 해당 의견을 failed_opinion_ids 로
3규모 상한변경 파일 수 / 라인 수 상한 초과전량 전량 되돌리고 kind=failed
4잔여물 검사워크스페이스에 untracked 파일이 생겼는가부분 삭제. checkout -B 는 untracked 를 지우지 않는다
리터럴 실증세 항의 차집합을 직접 조립한다
A ∈ literals(base 유닛)   # 옛 값이 있었고
A ∉ literals(head 유닛)   # 사라졌고
B ∈ literals(head 유닛)   # 새 값이 생겼다
⚠️ 함정 1 — 출현 횟수가 사라진다. extract_literals 는 (kind, key, value) 로 완전 dedup 한다. 「3곳 중 3곳 다 치환됐나」는 판정 불가 — 「그 값이 head 유닛에 더는 없다」까지만 말할 수 있다. 템플릿의 occurrences 가 unavailable 인 이유다.
⚠️ 함정 2 — 평문 용어 교체는 안 걸린다. 리터럴 5종(kv/unit/bool/code/link) 밖의 평문 교체는 아예 잡히지 않는다 → markdown_tree.section_text + 문자열 in 검사를 병행해야 한다. 템플릿의 text 슬롯이 그것이다.
⚠️ UnitLiterals.changed 를 믿지 말 것. 같은 키의 값이 여러 개일 때 정렬 후 위치로 zip 해 from→to 를 만들기 때문에 매핑이 어긋날 수 있다. 단일 치환 검증에는 위 3항 차집합을 직접 조립한다.

문서 계약 충돌

docs/mr-review-pipeline.html:554 가 v3.1 결정으로 못 박고 있다:

CLAUDE 단일 세션(호출 1회) — 최상위는 오케스트레이터. 3a · 3b · 3c 는 각각 독립 컨텍스트의 서브에이전트로 수행. 단계별 별도 CLI 호출 금지. 오케스트레이터는 의견 원문 · 문서 전문을 직접 읽지 않고 구조화 산출물과 영수증만 다룬다

3회 별도 호출은 이 문장을 정면으로 뒤집는다. 뒤집을 근거는 둘 있다.

  1. 실측 — headless claude -p 에서 --safe-mode 가 --agents 를 무력화하고, run_in_background 기본값 탓에 서브에이전트 결과 회수가 종료 코드 0인 채 조용히 실패한다 (스파이크 3회 + 격리 프로브 4조합, 실호출 $2 소요).단일 세션 오케스트레이션은 실패가 관측되지 않는 구조다
  2. 선례 — 나중에 설계된 mrdoc 이 이미 노드별 개별 codex exec 호출 + 산출물 파일 존재 검증으로 갔고(app/mrdoc/satellites.py), 그 판단이 docs/mrdoc-pipeline.html 에 문서화돼 있다.docs/mrdoc-migration-plan.md §3-A2 도 「멀티턴이 불안정하면 컨텍스트를 파일로 주입하는 단발 호출로 강등 가능」이라고 이미 열어 뒀다
또한 docs/mrdoc-migration-plan.md §2 가 revise 루프를 「변경 없이 유지」 대상으로 명시했으므로 이 역시 뒤집어야 한다.

실검증 (남음)

AI_RUNNER=staged 로 product-common !11 에 의견 1건 제출 → .revise/.../r*/ 아티팩트 8개 생성 확인 → 커밋이 md 만 건드렸는지 → 슬랙 재알림 · 리포트 확인. 대상 없는 의견(「존재하지 않는 절을 고쳐라」)을 넣어 되물음 + round 불변까지 확인.

미결 사항

  1. 「라운드 1 차감」의 정확한 의미. round 미증가로 해석했다. round - 1을 의도했다면 0에서 음수가 되는 경우의 가드가 별도로 필요하다
  2. 같은 파일에 성공 의견과 실패 의견의 편집이 섞였을 때. 파일 단위로만 분리 가능하다. 현재 구현은 「성공 의견이 만진 파일만 커밋」이고 그 귀속은 편집 영수증으로 한다. 더 엄격하게 가려면 편집을 의견 단위로 직렬화해야 하는데 호출 수가 늘어난다
  3. 대상 문서가 많을 때의 3b fan-out. 호출 3회 결정을 유지하면 배치 분할이 필요하다. mrdoc 의 fanout(기본 5) 패턴을 그대로 쓸 수 있으나 이는 단계 수가 아닌 같은 단계의 병렬 배치다
  4. 「커밋 없는 라운드」의 처리 규칙이 문서에 없다. 테스트(test_no_commit_round_sends_none_diff_stat_and_compare_url)로만 굳어져 있다. 이번 개정에서 같이 명문화하는 것이 좋다
  5. ai_max_budget_usd를 단계별로 쪼갤지 호출당 그대로 둘지 — 정리됨. 단계별 revise_stage_budget_usd 를 둔다. 값도 실측으로 정했다: 3b $0.247(5턴), 3c 무도구 $0.0287(1턴). 같은 입력에서 턴 수가 약 2배까지 흔들려 $0.5 는 실측 $0.247 짜리 단계를 떨어뜨렸다 — 상한은 폭주를 막는 장치이므로 실측의 ~6배인 1.5로 둔다
