왜 Python 인가

LLM 오케스트레이터였던 판에서는 「산출물 본문을 읽지 않는다」·「위성이 준 숫자를 합산하지 않는다」를 프롬프트로 막아야 했다. 200턴을 도는 동안 프롬프트는 잊히고 도구는 남는다. Python 구현에서는 그 경로가 원천적으로 부재다 — 코드에 없으면 일어나지 않는다.

그래도 규칙으로 남는 것

  1. 산출물 본문을 읽지 않는다. 상태가 필요하면 mrdoc status
  2. 위성이 준 숫자를 합산하지 않는다. 합산하면 리포트 숫자의 출처가 두 곳이 된다. 합산은 mrdoc collect. ledger 에는 리턴을 원문 그대로
  3. 위임 스펙을 직접 작성하지 않는다. dispatch 출력을 그대로 넘긴다. 부실해 보이면 그건 dispatch 버그다
  4. 팬아웃 5 초과 금지. 한 wave 를 여러 번으로 쪼개지 않는다. 쪼개면 조인 지점이 사라진다
  5. 위성을 임의로 재호출하지 않는다. 재호출은 비결정성의 유일한 입구다. 리턴 유실은 mrdoc status --receipt 로 회수
  6. exit code 를 무시하지 않는다. 0/4/2 이외는 abort

왜 리턴만으로는 안 되는가

위성 공통 규약 Report-first(첫 2 툴 호출 안에 스켈레톤 생성)와 RECEIPT copy(529 유실 시 회수)는 산출물 파일이 있어야 성립한다. 리턴만 두면 verifier 혼자 두 규약의 예외가 되고, 죽으면 감사 결과가 같이 사라져 재호출밖에 답이 없다 — 재호출은 비결정성의 유일한 입구다.

  • collect 가 직접 읽는다. 50-collect frontmatter 의 verify: {rounds, outstanding} 출처가 파일로 확정된다 — 오케스트레이터가 데이터 경로에서 빠진다
  • dispatch 가 재호출 스펙을 만든다. FIX 상세를 파일에서 읽어 SCOPE·CONTEXT·CONSTRAINTS 를 결정론적으로 생성한다. 리턴에는 개수만 싣는다
  • 오케스트레이터가 받는 것은 두 개뿐이다. REPORT 경로 + REQUIRED_FIXES 개수. 본문은 읽지 않는다

HARD LIMITS

  1. 남의 산출물을 수정하지 않는다. 고치면 저자가 되고 fresh context 가 무의미해진다. Write 는 40-verifier.md 한 개에만. 20-analysis/*.md 는 안 건드리고 FIX 에 대상 id 만
  2. 애매하면 ok 로 넘기지 않는다. 부당한 통과가 이 계층을 없앤다. FIX + 이유 한 줄
  3. 원문 안 읽고 판단하지 않는다. 읽은 것만 CHECKED. 못 읽은 항목은 UNCOVERED
  4. 문서 내용의 옳고 그름을 보지 않는다. 설명의 충실도만. 이상해 보이면 UNCERTAIN 한 줄
  5. 어휘 위반을 잡지 않는다. 그건 levelcheck 어휘 게이트. 값싼 게이트가 먼저 돈다
  6. 머지 의견 · 심각도 · 권고를 쓰지 않는다. 판정 자체가 없다. 스키마에 그 필드가 없다

CHECKED 의 의미는 reviewer.md 그대로 — "what you actually read, not what you were pointed at." 원문을 안 읽은 통과는 고무도장이다.

  exit 0  → out 의 블록 실행

파서 범위
^## (TYPE) (id)$ 정규식 + 그 아래 첫 yaml fence. 그 이상 안 본다
섹션 추가
템플릿에 없는 섹션 추가 금지. 생기면 warn — 프롬프트 드리프트 조기 감지
서술 라벨
설명 하나다. 위성이 쓰는 자연어 필드는 이것과 doc-verifier 의 why 뿐이다
템플릿 생성
파서의 렌더러가 만든다. 위성 프롬프트에 들어가는 산출물 템플릿 문자열을 손으로 쓰지 않고 파서 모듈의 render 함수로 만든다 — 프롬프트와 파서가 한 소스를 공유해야 드리프트가 물리적으로 불가능하다
필드 형태
스칼라는 고정 필드, 중첩은 yaml 블록. 리스트-객체는 한 줄 flow 만 — key: [{a: 1}, {b: 2}]. 블록 시퀀스(key: 다음 줄에 - {…})는 파서가 받지 않는다
RECEIPT
리턴 유실(529) 시 mrdoc status --receipt 가 회수한다. 재호출하지 않는다
이 두 줄이 실측 실패의 직접 원인이다. analyzer 프롬프트 템플릿은 리스트-객체를 블록 시퀀스로 쓰라고 지시했고 파서는 한 줄 flow 만 받았다 — 산출물이 통째로 파싱 실패했는데 파이프라인은 complete 로 끝났다. 테스트는 렌더러가 만든 인라인 flow 로 통과했다: 프롬프트 템플릿 모양을 담은 테스트가 0개였다.
