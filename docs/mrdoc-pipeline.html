왜 Python 인가

LLM 오케스트레이터였던 판에서는 「산출물 본문을 읽지 않는다」·「위성이 준 숫자를 합산하지 않는다」를 프롬프트로 막아야 했다. 200턴을 도는 동안 프롬프트는 잊히고 도구는 남는다. Python 구현에서는 그 경로가 원천적으로 부재다 — 코드에 없으면 일어나지 않는다.

그래도 규칙으로 남는 것

  1. 루프는 산출물 본문으로 분기하지 않는다. 상태는 dispatch.derive_state(). 사람이 볼 때는 status.format_status()(노드별 한 줄 — CLI 로 노출돼 있지 않다)
  2. 위성이 준 숫자를 합산하지 않는다. 합산하면 리포트 숫자의 출처가 두 곳이 된다. 합산은 collect 노드가 원자 인벤토리에서. ledger 에는 노드 완료 줄만 — 위성 리턴은 싣지 않는다
  3. 위임 스펙을 직접 작성하지 않는다. dispatch 출력을 그대로 넘긴다. 부실해 보이면 그건 dispatch 버그다
  4. 팬아웃은 배치 크기다. 한 wave 의 스펙은 전부 실행한 뒤에 조인한다. mrdoc_fanout(기본 5) 파일마다 analyzer 스펙 1개, 배치는 전부 같은 wave 에 나오고 순서대로(동시 실행 없이) 돈다. 조인 지점 = 스펙 실행 뒤의 툴 노드 패스
  5. 위성을 임의로 재호출하지 않는다. 재호출은 비결정성의 입구다. 유일한 재호출은 dispatch 가 정하는 fix 라운드(최대 2회). 리턴은 받지 않으므로 회수할 것도 없다 — mrdoc status --receipt 는 미구현
  6. abort 계약을 지킨다. 예외는 전부 abort: … 한 줄 + 2. 20 wave 안에 끝나지 않아도 2

왜 리턴만으로는 안 되는가

실행기는 위성의 리턴을 아예 받지 않는다 — codex exec 의 stdout 은 버려지고(비정상 종료 때 앞 500자만 로그), 남는 것은 파일뿐이다. 그래서 감사 결과는 반드시 파일이어야 하고, verifier 가 아무것도 쓰지 않으면 오케스트레이터가 FAILED 스텁을 대신 써서 verify.status: failed 로 저하한다 — abort 도, 임의 재호출도 하지 않는다.

  • collect 가 직접 읽는다. 50-collect 의 verify: {status, rounds, outstanding, counts_mismatch, audited, unaudited} 가 전부 이 파일의 블록에서 잰 값이다 — 위성이 적은 checked · required_fixes 는 읽지 않는다
  • dispatch 가 재호출 대상을 만든다. FIX 대상 ∪ invented/omitted 판정 유닛을 파일에서 읽어 SCOPE units … 로 넘기고, 사유 문장은 위성 모듈(_fix_mission)이 라운드 아카이브에서 다시 읽어 프롬프트에 붙인다
  • 오케스트레이터가 받는 것은 bool 하나다. 성공 = exit 0 · 기대 산출물 존재 · plan.check() 통과(verifier 는 존재만)

HARD LIMITS

  1. 남의 산출물을 수정하지 않는다. 고치면 저자가 되고 fresh context 가 무의미해진다. Write 는 40-verifier.md 한 개에만. 20-analysis/*.md 는 안 건드리고 FIX 에 대상 id 만
  2. 애매하면 ok 로 넘기지 않는다. 부당한 통과가 이 계층을 없앤다. FIX + 이유 한 줄
  3. 원문 안 읽고 판단하지 않는다. 읽은 것만 CHECKED. 못 읽은 항목은 UNCOVERED. 목록의 id 는 한 글자도 바꾸지 않는다 — 블록이 없는 유닛은 미검증 으로 잰다
  4. 문서 내용의 옳고 그름을 보지 않는다. 설명의 충실도만. 이상해 보이면 UNCERTAIN 한 줄
  5. 어휘 위반을 잡지 않는다. 그건 levelcheck 어휘 게이트. 값싼 게이트가 먼저 돈다
  6. 머지 의견 · 심각도 · 권고를 쓰지 않는다. 판정 자체가 없다. 스키마에 그 필드가 없다
  7. 카운트는 존재 모순만 잡는다. 「없다」고 쓴 변경에 실재 원자가 있거나, 서술한 변경에 대응 원자가 없을 때만 mismatch. 「n곳」과 「n항목」은 단위가 다를 뿐 — 숫자 차이만으로 불일치로 삼지 않는다(코드 HARD LIMIT 9)

CHECKED 의 의미는 reviewer.md 그대로 — "what you actually read, not what you were pointed at." 원문을 안 읽은 통과는 고무도장이다.

파서 범위
^## (TYPE)( id)?$ 정규식 + 그 아래 첫 yaml fence. 그 이상 안 본다. 서술은 닫힌 굵은 라벨(**설명** · **FILE_SUMMARY** · **한 줄** · **why**)과 이어지는 줄만. 툴 산출물 중 05-structure 는 frontmatter 없이 표 4개뿐이다
섹션 추가
템플릿에 없는 섹션 추가 금지. 파서는 모르는 블록을 조용히 무시한다 — warn 은 미구현이라, 드리프트는 필드가 비는 것으로(설명 누락 → fix 라운드) 드러난다
서술 라벨
위성이 쓰는 자연어는 유닛 설명 · FILE_SUMMARY 문단 · verifier 의 why(UNIT 의 굵은 라벨 · COUNTS 의 yaml 필드) · themes 의 한 줄 뿐이다
템플릿 생성
파서의 렌더러가 만든다. 위성 프롬프트에 들어가는 산출물 템플릿 문자열을 손으로 쓰지 않고 파서 모듈의 render 함수로 만든다 — 프롬프트와 파서가 한 소스를 공유해야 드리프트가 물리적으로 불가능하다
필드 형태
스칼라는 고정 필드, 중첩은 yaml 블록. 리스트-객체는 한 줄 flow 만 — key: [{a: 1}, {b: 2}]. 블록 시퀀스(key: 다음 줄에 - {…})는 파서가 받지 않는다
RECEIPT
세 위성 프롬프트가 복사를 요구하고 파서는 읽고 버린다. 설계했던 회수 경로(mrdoc status --receipt)는 미구현 — 실행기가 리턴을 받지 않으므로 회수할 대상도 없다
이 두 줄이 실측 실패의 직접 원인이다. analyzer 프롬프트 템플릿은 리스트-객체를 블록 시퀀스로 쓰라고 지시했고 파서는 한 줄 flow 만 받았다 — 산출물이 통째로 파싱 실패했는데 파이프라인은 complete 로 끝났다. 테스트는 렌더러가 만든 인라인 flow 로 통과했다: 프롬프트 템플릿 모양을 담은 테스트가 0개였다.
